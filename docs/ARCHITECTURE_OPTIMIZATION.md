> **문서 버전**: v1.0

> **프로젝트**: 오늘 주막 (`today-jumak`)  
> **핵심 과제**: LLM 응답 지연 개선, 클라우드 DB 지연 완화, API 호출 비용 최소화

## 1. 개요 및 병목 분석 (Bottleneck Analysis)

AI 기반 서비스는 일반적인 웹 서비스와 달리 **외부 LLM(대형 언어 모델)의 텍스트 생성 지연(평균 1.5초 ~ 3.5초)**과 **외부 클라우드 DB(Firestore) 쓰기 레이턴시**가 전체 사용자 경험의 핵심 병목으로 작용합니다.

현재 `today-jumak`은 사용자 이탈을 방지하기 위해 `setTimeout(2500ms)` 타임아웃 및 `localStorage` 0초 즉시 백업을 도입하였으며, 본 문서는 이를 한 단계 더 발전시킨 **다계층 캐싱 정책**, **비동기 스트리밍/낙관적 UI 패턴**, 그리고 **LLM 비용 최적화 설계**를 정의합니다.

---

## 2. 다계층 캐싱 정책 (Multi-Tier Caching Policy)

동일한 지역과 맛 조합(예: `지역: 속초, 맛: 🍯 달달함 + ⚡ 톡 쏘는 탄산`)은 추천 결과가 반복적으로 동일할 수 있으므로, 매번 비싼 LLM API를 재호출하지 않고 캐시 계층에서 즉각 반환하도록 설계합니다.

```mermaid
flowchart TD
    Req["사용자 추천 요청<br/>(지역: 속초, 맛: 달달함)"] --> L1{"L1: 브라우저 캐시<br/>(SessionStorage)"}
    L1 -->|HIT (소요: 0ms)| Res1["즉시 결과 렌더링<br/>(비용: $0)"]
    L1 -->|MISS| L2{"L2: Vercel Edge 캐시<br/>(CDN / SWR)"}
    L2 -->|HIT (소요: ~30ms)| Res2["Edge 캐시 결과 반환<br/>(비용: $0)"]
    L2 -->|MISS| L3["L3: Python Serverless<br/>& OpenAI LLM 호출"]
    L3 -->|소요: ~1.8s| Save["L1, L2 캐시 동시 갱신"]
    Save --> Res3["최종 결과 반환"]
```

### 2.1 L1 브라우저 클라이언트 캐시 (SessionStorage)
- **대상**: 사용자가 한 세션 내에서 이전에 눌렀던 조합을 다시 클릭하는 경우.
- **캐시 키(Cache Key)**: `jumak_rec_${region}_${tastes.sort().join('_')}`
- **TTL(유효 시간)**: 1시간 (또는 탭 닫을 때까지).
- **효과**: 네트워크 요청 0건, 응답 시간 **0.01초(즉각 반응)**.

### 2.2 L2 Vercel Edge / CDN 캐싱 (SWR 정책)
- **대상**: 서로 다른 사용자가 동일한 인기 조합(예: `서울 + 담백함`)을 요청하는 경우.
- **구현 방식**: Serverless 응답 헤더에 `Cache-Control` 설정.
  ```http
  Cache-Control: public, s-maxage=86400, stale-while-revalidate=604800
  ```
  - `s-maxage=86400` (24시간): 전 세계 Vercel Edge 서버에 24시간 동안 캐시 보관.
  - `stale-while-revalidate=604800` (7일): 캐시 만료 후 첫 요청 시 이전 캐시를 즉시 서빙하고 백그라운드에서 비동기로 갱신.
- **효과**: 글로벌 CDN 히트 시 응답 속도 **30~50ms**, LLM API 호출 횟수 대폭 감소.

## 3. 비동기 처리 및 UX 개선 패턴 (Async & UX Patterns)

### 3.1 낙관적 UI 업데이트 (Optimistic UI Updates) - 제보 기능
- **문제점**: 사용자가 인생 막걸리를 제보할 때 Firebase Firestore의 네트워크 왕복(RTT) 및 대기 시간으로 인해 2~3초간 화면이 멈춘 것처럼 느껴짐.
- **개선 패턴**:
  1. 사용자가 제보 버튼 클릭 즉시 `localStorage`에 **0초 만에 로컬 반영**.
  2. UI에 "장부에 기록되었소!" 모달을 즉시 표시하여 사용자 체감 대기 시간을 **0초**로 단축.
  3. 백그라운드에서 Firestore `addDoc()` 비동기 처리. (실패 시 재시도 큐에 보관).

### 3.2 타임아웃 레이스 패턴 (Timeout Race Pattern)
- **현재 구현**:
  ```javascript
  // 2.5초 타임아웃과 Firestore 저장을 경쟁(Race)
  const timeoutPromise = new Promise((_, reject) => 
    setTimeout(() => reject(new Error('TIMEOUT')), 2500)
  );
  await Promise.race([saveToFirestore(), timeoutPromise]);
  ```
- **개선안**: 통신이 2.5초를 초과하더라도 로컬 스토리지 데이터로 자동 폴백(Fallback)되어 사용자는 실패를 경험하지 않음.

### 3.3 LLM 스트리밍 응답 (Server-Sent Events / Streaming)
- 전체 답변 텍스트(300~400토큰)가 모두 생성될 때까지 대기(약 2초)하지 않고, 첫 토큰이 나오는 즉시(**TTFT: Time to First Token ~350ms**) 브라우저에 한 글자씩 타이핑 효과로 렌더링하여 체감 지연 시간을 극적으로 단축.

## 4. 비용 최적화 설계 (Cost Optimization)

LLM API는 **입력 토큰(Prompt Tokens)**과 **출력 토큰(Completion Tokens)**의 총합에 비례하여 요금이 청구됩니다.

### 4.1 프롬프트 경량화 및 토큰 압축
- **기존 프롬프트**: 장황한 배경 설명과 중복된 예시 문장 포함 (약 520 토큰).
- **최적화 프롬프트**: 불필요한 수식어를 제거하고 필수 4문단 규칙만 구조화하여 전달 (약 210 토큰, **59.6% 절감**).

### 4.2 `max_tokens` 상한선 고정
- 무제한 생성을 방지하고 주모의 4문단 답변에 적합한 최적 길이인 `max_tokens: 450`으로 엄격히 제한하여 비정상적인 토큰 낭비 및 무한 생성 루프를 원천 차단.

### 4.3 입력 검증을 통한 무의미한 API 호출 차단 (Fast Fail)
- 프론트엔드와 백엔드 진입점에서 지역명 공백 체크, 특수문자 필터링을 수행하여 유효하지 않은 요청은 LLM API 호출 전 `400 Bad Request`로 즉시 반환 ($0 소모).

### 4.4 최적화 전후 정량적 비교표

| 지표 | 최적화 전 (As-Is) | 최적화 후 (To-Be) | 개선율 |
| :--- | :---: | :---: | :---: |
| **평균 응답 속도 (TTFB)** | ~2,500ms | **~450ms** (캐시 히트 시 30ms) | **82% 단축** |
| **요청당 평균 토큰 소모** | ~850 토큰 | **~380 토큰** | **55.3% 절감** |
| **1만 건 호출 시 예상 비용** | 약 $12.50 | **약 $3.80** | **69.6% 절감** |
| **제보 등록 체감 대기 시간** | ~2,500ms (네트워크 대기) | **0ms** (낙관적 UI 즉각 반응) | **체감 100% 개선** |
| **네트워크 단절 시 데이터 유실** | 유실 위험 | **0%** (`localStorage` 즉시 백업) | **안정성 확보** |
